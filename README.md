# 친친소 · 대화형 신청

빌드 없는 정적 HTML/CSS/JS. 현재 작업 브랜치: `dain-chat-ui`.

## 로컬 확인

레포 폴더에서 정적 서버를 실행한 후 `http://localhost:8000/?demo=1`을 연다.
예: `python3 -m http.server 8000` (설치된 Python 필요).
`demo.html`을 더블클릭해 브라우저로 열어도 체험 가능하다.

데모는 서버에 아무것도 전송하지 않는다. 사진 3~5장과 필수 항목, 동의를 입력하면 완료 → 심사중 → 합격/불합격 미리보기를 확인할 수 있다. 두 주선자 모두 선택 가능하며 성별과 독립적이다. 이전, 요약 수정, 내 정보 보기 및 전체 수정 기능을 제공한다. 사진과 작성 중 내용은 메모리에만 두므로 새로고침하면 미제출 내용은 사라진다. 실제 접수 후에는 현재 탭의 sessionStorage 접수 확인 정보로 서버에서 다시 읽는다. 접수 확인 정보는 비밀번호처럼 취급하고 공유하지 않는다.

## 기존 데이터와 호환

기존 Apps Script URL, POST, `text/plain;charset=utf-8`, 평평한 한글 키 JSON 객체를 유지한다.
기존 필드 `연령대`, `유입경로`, `성별`, `만족도`, `유용한점`, `추천의향`, `좋았던점`, `개선점`을 유지한다. 연령대는 현재 연도-출생연도로 산출하며, 신청과 무관한 기존 설문 항목은 빈 문자열로 둔다. 유입경로의 선택 값은 새 명세에 맞춰 변경했다. 기존 데이터 행은 수정하지 않는다.

추가 필드: `주선자`(기존 내부 페르소나 f/m 유지), `이름`, `출생연도`, `키`, `생활권`, `직업`, `학교`, `MBTI`, `취미`, `음주`, `흡연`, `종교`, `이상형`, `제외조건`, `중요조건`, `연봉`, `자산`, `추천인`, `연락처`, `개인정보동의`, `개인정보동의일시`, `신청ID`, `사진`. 연락처는 실제 소개 연락을 위해 추가했다. 표시명은 다민/정진으로 통일한다. 사진은 전송 때 파일명·MIME·base64 데이터 배열이며, 시트에는 비공개 Drive 파일 ID와 이름만 저장한다.

서버 관리 필드: `심사상태`, `수정일시`, `접수토큰해시`. `_action`, `_token`은 요청 제어용이며 일반 신청 필드가 아니다. 심사상태는 `pending`, `approved`, `rejected`. 서버는 헤더 이름으로 매핑하고 없는 열만 끝에 추가한다. 기존 열 순서와 알 수 없는 추가 열은 보존한다.

요약은 AI 분석으로 가장하지 않고 세 자유답변을 원문 그대로 보여준다. 중요도 재분류는 사용자가 직접 수정한다. 사진은 3~5장, 각 5MB 이하 JPG/PNG/WebP. 선택적인 연봉/자산, MBTI/종교/추천인은 생략 가능하다.

## 실제 서비스 연결 — 운영자 적용 필요

현재 저장소에는 기존 Apps Script 서버 소스나 배포 권한이 없다. 기존 서버의 새 필드 지원 여부는 검증할 수 없으며, 프런트엔드 수정만으로 사진 저장이나 심사가 작동한다고 보장하지 않는다. 실제 서버로 테스트 개인정보를 전송하지 않았다.

1. 기존 Apps Script 소스를 백업하고 기존 기능을 확인한 뒤 `server/Code.gs`를 적용한다. 기존 자동화/트리거가 있다면 충돌 없이 통합한다. Script Properties의 `SPREADSHEET_ID`에 기존 응답 시트 ID를 지정한다. 첫 번째 탭을 사용하므로 다른 탭이 응답 탭인 경우 코드를 수정한다.
2. 시트와 Drive에 접근하는 운영자 계정으로 웹 앱을 배포한다. 기존 배포를 업데이트하면 기존 URL이 유지된다. 새 배포라면 `app.js`의 ENDPOINT만 변경한다. 시트/사진 폴더는 공개하거나 링크 공유하지 않는다. 자동 생성 폴더의 운영자·공유 권한을 확인한다.
3. 운영자의 개인정보 처리방침(처리자, 보유기간, 삭제 요청 연락처)을 확정하고 `app.js`의 `PRIVACY`에 `operator`, `retention`, `contact`를 입력한 뒤 공개한다. 세 값이 비어 있으면 실제 접수는 차단된다. 제공된 서버는 자동 보존기간 만료/삭제 작업을 포함하지 않으므로 운영 정책에 맞춰 설정한다.
4. 스테이징 시트에서 저장→사진 비공개 확인→새로고침 조회→정보 수정→재심사 대기→결과 조회를 검증한다. CORS/Apps Script 접근 권한과 대용량 이미지 전송도 실제 배포에서 확인해야 한다.
5. 시트의 `심사상태`를 `approved` 또는 `rejected`로 바꾸면 사용자가 ‘상태 새로고침’을 눌렀을 때 결과가 반영된다. 사용자의 정보 수정은 `pending`으로 되돌린다. 사용자가 실제 심사결과를 선택하는 기능은 없다. 자동 연락이나 관리 콘솔은 포함하지 않는다.

서버는 `{ok:true,schemaVersion:2,id,token}`으로 접수를 확인한다. 기존 서버가 이 계약을 지원하지 않거나 전송 오류가 발생하면 완료 화면을 표시하지 않는다. 같은 신청ID 재시도는 새 행을 만들지 않는다. 기존 서버가 응답 계약 없이 저장만 하는 경우는 프런트엔드에서 저장 여부를 알 수 없으므로 새 서버 적용 전에 실제 제출을 사용하지 않는다.

## 검증

`node tests/flow.cjs`: 두 주선자 × 14단계 렌더링, 필수 입력/연도/키/MBTI/연락처/사진 수/동의 검사, 성별과 주선자 독립성, 요약 수정값 보존, 데모 접수, 세 심사 상태, HTML 이스케이프, 기존 서버 응답 및 네트워크 오류 처리를 검증한다. 가벼운 DOM 대역을 사용하는 로직 테스트이며 실제 브라우저 레이아웃 검증을 대체하지 않는다.

이 작업 환경에서는 브라우저 실행 및 로컬 파일 열기 정책 제한으로 시각 검증은 완료하지 못했다. 실제 Apps Script 저장/Drive 권한/심사 조회는 배포 후 검증이 필요하다.

## 보라색 세 화면 구성

서비스 소개와 성별 선택을 첫 화면에 통합했다. 두 번째 화면은 다민/정진의 프로필, 소개 및 메시지 미리보기가 있는 대화 목록이다. 선택하면 세 번째 화면인 채팅방으로 바로 진입한다. 기본정보·생활습관·선택 경제정보·유입정보는 한 질문씩 입력하며 이전 답변은 말풍선으로 누적된다. 이전 버튼으로 직전 답변을 수정할 수 있으며 저장 필드와 서버 계약은 변경하지 않았다.

채팅 UI는 상단 중앙 프로필 헤더 / 스크롤 메시지 영역 / 하단 고정 composer로 분리했다. 입력·선택지는 composer로 이동하며 질문은 말풍선만 표시한다. Visual Viewport 높이와 safe-area를 반영한다. 393×852 화면에서 헤더, 입력창 및 메시지 전송을 브라우저로 검증했다. 실제 iOS 키보드는 별도 기기 확인이 필요하다.

## 현재 디자인: 틸 v0.2

기존 컬러 설명보다 `design/SPEC.md`를 우선한다. 철학→결정→토큰→컴포넌트→레이아웃→화면→렌더 비평을 기록했다.
`design/tokens.json`을 수정하고 `node design/build.cjs`를 실행하면 CSS 생성 및 대비/출처 검증을 수행한다.
`design/REVIEW.md`에 검증 결과와 남은 게이트를 구분했다.
기존 f/m 및 한글 저장 필드·전송·심사 상태 값은 변경하지 않았으며, 사용자 표시를 자동안내/운영자 확인/작은 자리 초대에 맞춰 정리했다.

현재 팔레트는 design/SPEC.md v0.3의 좌측 #FEE0E2 / 우측 #F1ECFF / 미색 배경을 따른다. Pretendard Variable v1.3.9를 assets/fonts에 포함하여 별도 컴퓨터 설치나 외부 CDN 없이 로드한다. 본문400·이름/버튼600·제목700, 본문16px 유지.
